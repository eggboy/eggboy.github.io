Assumptions & Methodology
  • How the VM count is derived. Each VM (one node of the SKU) serves up to its max users at the target rate — the largest batch that both (1) fits weights + KV cache in VRAM and (2) still sustains the per-user token rate. The tool then sizes VMs needed = ⌈your users ÷ max users per VM⌉, spreading users evenly across identical replicas behind a load balancer. A SKU is marked ✗ only when even one VM can't host a single user at the target — adding more VMs can't fix a per-user ceiling.
  • Decode is a roofline. Per generated token, the batch step time is t_step = max(memory_time, compute_time) / efficiency:
    • memory_time = (weights + N × KV_per_user) / total_HBM_bandwidth — weights and all sequences' KV are read from HBM each step.
    • compute_time = (2 × params_B × N) / (total_TFLOPS × 1000) — matmul FLOPs for the batch.
    Per-user rate = 1 / t_step; aggregate = N / t_step. Tensor parallelism pools bandwidth and FLOPs across the SKU's GPUs.
  • Per-user speed drops as users rise because KV reads grow with concurrency and context. Each VM is loaded only up to the point where it still meets the target, so the tool reports the per-user rate at that balanced per-VM load, and the max users a single VM sustains.
  • KV cache (hybrid). Qwen 3.6 is a DeltaNet + attention hybrid: only the full-attention layers cache KV. KV_per_user = full_attn_layers × 2 × kv_heads × head_dim × bytes × (input + output). DeltaNet layers use a small fixed recurrent state (excluded).
  • Weights. FP8 = 1 byte/param (27 GB); FP16 = 2 bytes (54 GB).
  • FP8 compute. H100/H200 run FP8 tensor cores (≈2× FP16 TFLOPS). no FP8 A100, A10 and T4 have no FP8 tensor cores — FP8 weights are read from HBM as 1 byte (bandwidth benefit) but dequantized to FP16 for matmul, so their compute uses FP16 TFLOPS.
  • Memory-bound by design. At single-digit-to-hundreds batch sizes, 27B decode is almost always HBM-bandwidth bound, so faster memory (H100/H200) raises per-user speed more than extra FLOPs.
  • Usable VRAM = 90% of card memory. Memory-fit and "max users" reserve ~10% for activations, allocator fragmentation, CUDA/NCCL context and paged-KV block tables (≈ vLLM's default gpu_memory_utilization).
  • Units. Decimal GB throughout (1 GB = 10⁹ bytes), matching NVIDIA bandwidth (GB/s) and marketed GPU memory, so memory_time = GB / (GB/s) has no hidden GiB conversion error.
  • Context capping. If input + output exceeds Qwen 3.6's 256K window, the calculation is capped and flagged ⚠️.
  • Azure SKUs. GPU counts, memory, and bandwidth from Azure VM documentation and NVIDIA datasheets. NC/NV = inference- and visualization-optimized (1–4 GPUs); ND = 8-GPU NVLink/NVSwitch. Multi-GPU assumes tensor parallelism with full memory pooling.
  • Multi-GPU is an optimistic upper bound. Pooling all GPUs' bandwidth/FLOPs ignores tensor-parallel all-reduce, kernel-launch latency and lower utilization at small batch — so single-stream rates on 8-GPU SKUs (e.g. ~1000+ tok/s) are a ceiling, not a guarantee. Also, with only 4 KV heads the KV cache may not shard cleanly across TP=8 (some engines replicate it), which can raise KV memory/bandwidth on ND SKUs.
  • This is a planning estimate (steady-state decode). It ignores prefill/TTFT, attention FLOPs, scheduler overhead and network. Validate with a load test before committing.
